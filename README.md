# Betwin Odds Radar

Betwin 是一个本地运行的中国竞彩历史赔率分析网站。正式预测以相似历史比赛的真实赛果分布为核心；尚未通过时间顺序验证、独立门禁和人工批准的高级模型只用于离线研究。

## 环境

- Node.js 22 或更新版本
- Python 3.12 或兼容版本
- Python 依赖见 `requirements.txt`
- 默认 SQLite 数据库：仓库根目录 `betwin.db`

安装 Python 依赖：

```bash
python3 -m pip install -r requirements.txt
```

项目没有第三方 Node 依赖，也没有前端构建步骤。

## Git 备份范围

仓库保存代码、配置、文档和小型研究报告，不包含密钥、SQLite数据库、原始Excel/比赛JSON、备份、缓存以及大体积逐场研究和预测冻结档案。忽略规则只阻止上传，不会删除本地文件。换电脑后需要自行恢复这些本地数据或按下方流程重新导入；旧赛前冻结及账本应另行备份，不能靠重新预测恢复。仅克隆代码并不等于恢复完整运行数据，依赖本地数据库的测试也需要先准备数据。

## 启动

```bash
npm start
```

默认地址为 `http://127.0.0.1:8765/`。可使用 `PORT` 修改端口，使用 `BETWIN_DATABASE_PATH` 指定其他数据库。

## 数据更新

数据来源约束：只有导入模块可以读取 Excel。预测、统计、报告及回测统一读取数据库，不能直接分析 xlsx，也不能因旧来源文件名排除新入库数据。来源文件名和原行号用于追溯；每日增量按数据库批次处理。

`report:goal-multiples` 与网页倍率统计均读取完整 `historical_goals`，不要求胜平负、让球记录同时齐全。报告显示全库样本数，明细按入库批次及记录 ID 倒序；符合倍率条件的场数是筛选结果，不等于全库数量。仅用于显示的比分按数据库外键关联，缺比分不排除进球样本。

旧研究脚本 `report:goal-zero`、`compare:league-hierarchy`、`scripts/test_calibration*.mjs`、`scripts/test_tolerance_ladder.mjs` 仍保留当时的单来源实验协议，启动时明确提示数据库子集范围；它们不直接读取 Excel，结果也不能作为全库结论。不要简单拼接来源或按重复行号排序后冒充新的时间验证；全库批次回测使用 `backtest:rolling`，正式平滑验证使用 `model:tune-smoothing`。

### 进球双选对照研究

`npm run compare:goal-pairs` 只读数据库，比较当前未平滑原模型、去水赔率基准、历史与市场概率融合。固定历史权重候选为25%/35%/45%/50%/75%，前60%（扣除预热）只用于选参，中间20%验证，末20%作已观察数据诊断；各方案都只选两个进球档位，在同一批可预测比赛上比较。报告并列展示所有权重；35%/45%是在旧结果已观察后追加的探索，不能以末段最优值重新选参或宣称独立验证通过。

每日增量使用数据库入库批次和记录ID，整批预测后才纳入训练，划段不拆批次；不同天文件行号重复不影响回测。旧累加数据没有批次内日期，仍按数据库保留的来源顺序独立回放，作为增量的初始历史池；不读取原Excel，也不声称入库先后等于真实比赛日期。盘口关联按数据库外键，缺少关联不排除进球研究样本。

报告同时检查双选覆盖率分箱、固定50%/55%筛选和开发段拟合的覆盖率截距校准。校准只修正概率表达，不改变选择或命中数；验证不稳定时不启用。该研究针对单场双选，不生成串关，不保证收益。

每次保存新的 `data/goal-pair-research/<时间>/report.md`、`report.json` 和逐场档案，不覆盖旧研究或赛前冻结。可用 `--output=/absolute/path/new-report.json` 指定新路径，已有路径会报错。无需每次更新数据都手动运行；它不会修改正式数据库、页面概率或生产批准，也不会自动冻结新实验或调用付费AI。未来验证尚未启用，历史回测不可当作赛前实测。

### 日常更新比赛

只更新当天 JSON：

```bash
npm run db:update-matches
```

此命令会在JSON导入后自动冻结A原模型、B近期状态、C历史交锋、D两者结合的实验预测。只有代码和数据库一致的服务才会复用；服务未运行或版本不符时自动启动临时服务，完成后自动关闭，不关闭原服务。同一批数据在同一冻结协议下重复执行会自动去重，不能把赛后补算当作赛前预测。

服务会在下一次接口请求或自动检查时重新加载变更的配置，并依据当前历史水位重新校验批准与可靠性。更新历史或验证配置后不再需要每天重启；更新服务代码后仍须重启一次，浏览器刷新后使用新版本。冻结期间配置或算法版本变化会中止本批，请更新完成后重试。冻结协议升级为 `context-pilot-v5-runtime-versions`，旧档案保留，A/B/C/D 的数学模型及 TypeSafe E 协议未改变。

单场结论区区分尚未验证、验证过期、样本不足、验证未通过及本场未通过筛选，不把未通过验证解读为已经证明与市场持平。总进球双选只使用独立双选报告及其本场筛选条件；同联赛、自定义范围或平滑后的概率不沿用未经验证的双选报告。

日常执行默认只显示一行结果；需要查看数据库统计、逐场进度和跳过原因时，使用 `BETWIN_VERBOSE=1 npm run db:update-matches`。

### TypeSafe E组实验

`db:update-matches` 在原 A/B/C/D 冻结成功后自动生成独立 E 组，不修改正式页面概率或原四组档案。E 使用原有状态、交锋特征加 TypeSafe 情境特征；另存同一训练池的 `Dcontrol`，避免把训练样本不同误认为 AI 提升。胜平负、让球和进球均独立训练，总进球同时冻结单选与双选。

- 服务端通过 `TYPESAFE_API_KEY` 读取凭证；不写入源码、网页、数据库或报告。没有 key、接口失败、预算耗尽或训练不足时，明确跳过 E，保留原预测。
- 使用固定 `jev-1.13.0`，一次问近期主队状态、客队状态、战绩可比性、交锋证据和进球环境五个问题。只上传白名单中的匿名战绩、比赛类型、主客场和相对天数，不传球队姓名、真实日期、赔率、账本和目标赛果；缺失的伤停、阵容及对手实力不补造。
- 答案是学习特征，不是比赛胜率。已有赛前快照可以事后提取特征用于训练，不能冒充当时已经生成的 E 组预测。
- 缓存、模型系数、独立冻结和结果报告位于 `data/typesafe/`。相同输入、问题和模型复用缓存，已成功冻结的 E 不重算；失败项可以下次补试，但已知目标赛果后禁止补预测。
- 默认每次最多 40 次请求、每天最多 60 次、每日估算费用上限 0.10 美元（北京时间），单次超时 12 秒、最多重试一次、调用阶段最多 120 秒。失败及重试也占用预算，并发同资料不重复调用。费用按固定模型当前每百万输入 token 0.042 美元计算，不是供应商账单硬限额；价格变动需复核。

日常仍只需运行原命令。可选命令：

```bash
# 首次预备一小批旧冻结资料的情境特征；不生成过去的预测、不改正式库
npm run typesafe:prepare

# 更新赛果后核对已冻结 E，与 A、D、同训练池 Dcontrol 比较
npm run report:typesafe
```

`typesafe:prepare` 每次最多新增 24 次历史特征请求；自动预测优先调用当前比赛，再用剩余预算补充历史特征。每玩法至少 20 条有效同版本训练记录才生成 E，这是探索门槛，不代表模型有效。成绩报告只统计 E 冻结后才结算、且实验启动时未知的比赛，显示命中率、进球双选命中率、LogLoss、Brier 和成对时间块区间；不自动上线。

临时关闭：`BETWIN_TYPESAFE_ENABLED=0 npm run db:update-matches`。限额可通过 `BETWIN_TYPESAFE_MAX_REQUESTS`、`BETWIN_TYPESAFE_DAILY_REQUESTS`、`BETWIN_TYPESAFE_DAILY_USD` 下调；隔离测试使用 `BETWIN_TYPESAFE_DIR`。要单独处理特定的当前四组报告，可运行 `npm run typesafe:predict -- --parent=/absolute/path/to/pilot.json`，旧来源或已结算目标不会被事后补算。

接口及价格依据：[TypeSafe HTTP API](https://docs.typesafe.ai/api)、[模型与价格](https://docs.typesafe.ai/models)。本功能不提供额外比赛数据，也不保证提高命中率或盈利。

少量更新历史 Excel，并按需重验正式可靠性规则：

```bash
npm run db:update-history
```

历史数据现在只从每天覆盖更新的 `history.xlsx` 增量导入，数据库保留此前的历史。重复内容不重复入库，也不改变首次入库批次；来源文件行号只用于追溯。

导入成功后会自动复盘已冻结的 A/B/C/D/E 预测，不需要先启动网页，也不用额外执行预测命令。此步骤只读取冻结选择和数据库赛果，不调用 AI、不训练、不重算旧预测、不修改正式概率。

在 **实战记录 → 预测效果对照** 查看结果：

- A 就是原模型；分别展示胜平负、让球胜平负、进球单选及双选的命中数、命中率和较 A 多中/少中的场次，另列 LogLoss、Brier。
- 同协议、同算法、同玩法使用共同比赛；含 E 的表只比较 E 实际冻结的 A/B/C/D/Dcontrol/E，不与四组表的全部样本混算。
- 可切换累计、最近一批、最近 30 场已结算。最近一批指最晚新增有效冻结的批次；重复冻结不增加样本，待结算不按失败计分。
- 展开未完成与排除原因可查看资料不足、未生成、重复冻结及赛果歧义等。旧任务未保存原因时明确标记未知，不猜测失败原因。

单独重新核对、但不导入数据时，可选运行 `npm run report:prediction-audit`。报告追加到 `data/prediction-audit/`，`latest.json` 保存最新派生结果；页面的重新核对赛果按钮只读核对，不导入文件。开发隔离可设置 `BETWIN_AUDIT_DIR`、`BETWIN_CONTEXT_PILOT_DIR`，数据库及 E 缓存沿用已有路径环境变量。

核对以赛果首次入库或结算时间判断冻结先后，缺少真实比赛日期时不能宣称严格赛前认证。少量比赛多中几场不证明稳定提升，也不会自动上线候选模型。

`npm run backtest:rolling` 和日常可靠性验证从数据库读取累积历史：每日数据按入库批次递增，整批预测完成后才把该批赛果加入训练。旧四个累加文件的存量保留各自原有顺序，作为新批次的初始历史池。入库顺序是无比赛日期情况下的时间代理，不代表真实开赛时间；补录很早的比赛需要额外标注，不能当作新的未来验证。

完整导入、离线报告、生产锁验证和测试：

```bash
npm run db:refresh
```

完整刷新耗时较长，不应作为每天少量数据更新的默认命令。

已结算比赛的近期状态与历史交锋时间顺序回放：

```bash
npm run evaluate:context-history
```

该命令只读账本中预测当时冻结的状态资料，逐批只用目标预测前已结算比赛训练，输出 `data/context-history-report.json` 和 Markdown 报告，不修改正式模型。

## 生产安全边界

- 正式 SPF/HHAD 阈值固定为 `±7%`，总进球使用独立生产匹配口径。
- 固定防零层使用总先验质量 `m=1.5`。
- `data/*-config.json` 是候选或研究产物，不能自行启用生产功能。
- 高级模块必须通过概率、ROI、版本与参数一致性门禁，并由对应 `data/*-production.json` 明确批准。
- 当前批准文件默认保持 `runtimeEnabled: false`。
